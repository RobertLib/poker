# App Store metadata

The App Store Connect texts, kept in the project. Nothing is uploaded
automatically — open the file, copy the contents, paste it into the matching
field in App Store Connect.

The folders are named after the fastlane convention (`cs`, `en-US`, `en-GB`), so
if you ever decide to move to `fastlane deliver`, renaming `AppStore/` to
`fastlane/metadata/` is all it takes.

## Where everything goes

App Store Connect → **Apps → Ace High → iOS App → 1.0 Prepare for Submission**.
There is a language switch at the top — every field is filled in separately for
each language.

| Field in App Store Connect | File | Limit | Currently |
|---|---|---|---|
| App Name | `<language>/name.txt` | 30 characters | 29 / 29 / 28 |
| Subtitle | `<language>/subtitle.txt` | 30 characters | 29 / 28 / 29 |
| Promotional Text | `<language>/promotional_text.txt` | 170 characters | 159 / 159 / 142 |
| Description | `<language>/description.txt` | 4000 characters | ~2300 |
| Keywords | `<language>/keywords.txt` | 100 characters | 91 / 96 / 95 |
| What's New in This Version | `<language>/release_notes.txt` | 4000 characters | ~380 |
| App Preview and Screenshots | generated by the scripts, see [screenshots.md](screenshots.md) | 1–10 images | 8 + video |

Alternative names, subtitles and keyword sets, the reasoning behind the ones in
use, and what the competition looks like are in
[alternatives.md](alternatives.md).

Checking the limits:

```bash
python3 - <<'PY'
import os
lim={'name.txt':30,'subtitle.txt':30,'keywords.txt':100,
     'promotional_text.txt':170,'description.txt':4000,'release_notes.txt':4000}
for loc in ('cs','en-US','en-GB'):
    for f,m in lim.items():
        n=len(open(os.path.join('AppStore',loc,f),encoding='utf-8').read().rstrip('\n'))
        print(f'{loc:6}{f:22}{n:5}/{m}', 'OK' if n<=m else 'OVER!')
PY
```

## Which localisations to create, and why three

Keywords never combine across languages — each localisation is its own search
index — but **most storefronts index two of them**, so a second language is free
extra keyword space in the same country rather than a different market.

| Storefront | Indexes | What that buys |
|---|---|---|
| United States | English (U.S.) + Spanish (Mexico) | `es-MX` would double the US pool |
| Czechia | **Czech + English (U.K.)** | `en-GB` doubles the Czech pool |
| United Kingdom, Ireland, Australia, New Zealand | English (U.K.) | `en-GB` is the primary there |

So the three folders here are:

- **`en-US`** — primary language of the record, and what most English storefronts
  read.
- **`cs`** — primary in Czechia.
- **`en-GB`** — primary in the UK/Ireland/Australia/New Zealand *and* the second
  index in Czechia. Same description as `en-US` with British spelling.

  Its keyword set is close to the `en-US` one **on purpose**, and that is a
  deliberate trade rather than an oversight. There is a temptation to fill `en-GB`
  with whatever `en-US` left out, so that the Czech storefront indexes twice as
  many words — but `en-GB` is the *only* index those four English storefronts
  have, and they are worth far more traffic than Czechia's second slot. So it
  carries the strong general set, and the handful of terms it does differ on
  (*bots*, *heads up* in place of *ai*, *chips*) are the bonus Czech coverage.
  Only the subtitle is properly different, because a subtitle is cheap to vary
  and is read by a human either way. The name is identical on purpose — brand
  consistency is worth more than the terms a second name would add.

`es-MX` is the obvious next one (it would double the US keyword pool for the cost
of a translation), and it is *not* included here: the app's interface is English
and Czech only, so a Spanish-speaking visitor would arrive at an English app.
That is allowed, and plenty of apps do it, but it trades conversion for reach.
Worth trying once there is enough traffic to measure the trade rather than guess
at it.

## Notes on the individual fields

- **App Name** — has to be globally unique, and it is the single strongest
  ranking signal. Plain "Ace High" would be invisible, hence
  `Ace High: Offline Texas Poker`: it carries *poker*, *texas* and *offline* while
  still reading like a title. On the home screen the app stays just "Ace High"
  (`INFOPLIST_KEY_CFBundleDisplayName`), which Apple does not mind — the home
  screen name only must not differ in *meaning*.
- **Subtitle** — the second strongest signal and the line people actually read in
  search results. It adds the terms the name could not fit (*holdem*, *bots*,
  *no ads*) rather than repeating it.
- **Keywords** — separate with commas and **no spaces** (a space counts towards
  the limit). Do not repeat words already in the name or subtitle, Apple indexes
  those separately; that is why *poker*, *texas*, *offline* and *holdem* are
  missing from the lists.
- **Promotional Text** — the only field that can be changed without a new build
  and without review. Useful for seasonal or topical messages.
- **What's New** — for a first release the field often does not appear at all; if
  App Store Connect does not offer it, skip it and use it from version 1.1 on.

## Settings that are not filled in with text

**App Information** (shared across all languages):

- Primary Category: **Games → Card**
  (matches `LSApplicationCategoryType = public.app-category.card-games`)
- Secondary Category: **Games → Casino** — where people browsing for poker
  actually look. If you would rather not sit next to the slot machines,
  Games → Strategy is the honest alternative; it charts worse for this genre.
- Content Rights: contains no third-party content
- **Gambling: No.** That declaration is about *real money*. Ace High has none,
  so it stays off — which also keeps you clear of the rule that gambling apps
  must be submitted by an organisation rather than an individual.

**Age Rating: 18+, and it is not a choice.** In the Chance-Based Activities step,
Simulated Gambling has to be answered **Frequent** — the whole app is a poker
table — and Apple maps that to 18+ in every country. Answering *Infrequent* would
give 13+ and would be a false answer. Every comparable app checked on the store
is 18+ for the same reason, and Apple's own *Texas Hold'em* still shows the
pre-2025 equivalent, 17+. Everything else in the questionnaire is None: no
violence, no chat, no links out, no contests, no loot boxes, no unrestricted web
access.

Two things follow from 18+ that are worth knowing before you plan any marketing:

- The app is hidden from anyone with content restrictions set below 18, so it will
  never be an option for a family account. The "no ads, no purchases" angle in the
  copy is aimed at adults who are tired of freemium chip grinding, not at parents.
- **Korea** classifies anything with simulated gambling as unsuitable under 19 and
  wants a GRAC certificate for it. Either obtain one or deselect Korea under
  Pricing and Availability; leaving it selected without one invites a rejection
  rather than a quiet failure.

**Pricing and Availability:** Free, all countries (minus Korea, above).

**App Privacy:** click *Get Started* → **"No, we do not collect data from this
app"**. The game has no networking code, no third-party SDKs, and stores
everything in UserDefaults on the device (declared in
`poker/PrivacyInfo.xcprivacy`, reason CA92.1). A **privacy policy URL is still
mandatory** — the text is ready in [privacy-policy/](privacy-policy/), it just
needs hosting somewhere (GitHub Pages, a gist, your own site) and the URL pasted
into the *Privacy Policy URL* field.

**Support URL:** a mandatory field. The project's GitHub page or a simple page
with an e-mail address will do.

**Marketing URL:** optional, feel free to leave it empty.

**Encryption:** `ITSAppUsesNonExemptEncryption = NO` is set in the project, so the
export compliance question never appears when the build is uploaded.

**App Review Information** → the note for the reviewer is in
[review-notes.txt](review-notes.txt). It leads with the play-money point, because
that is the only thing about this app a reviewer might reasonably wonder about.
The game needs neither an account nor a demo login — leave *Sign-in required*
switched off.

## Release procedure

1. Xcode → Signing & Capabilities, check team `K6GM85X5D7`, bundle ID
   `cz.rob.poker`.
2. App Store Connect → **Apps → +** → new record, bundle ID `cz.rob.poker`,
   primary language **English (U.S.)** (the fallback for every storefront without
   its own localisation, so this is the one that decides reach), SKU e.g.
   `acehigh-001`.
3. Add the other two localisations (App Information → language switch, top right):
   **Czech** and **English (U.K.)**.
4. Fill in the texts from this directory. The screenshots and App Preview are not
   in the repo — build them with `Tools/appstore_media.sh` and upload them, see
   [screenshots.md](screenshots.md) for details. `en-GB` has no media of its own;
   upload the `en-US` set into it.
5. Xcode → Product → Archive → Distribute App → App Store Connect → Upload.
6. Wait for the build to process (10–60 min), then select it in the *Build*
   section.
7. Fill in App Privacy, Age Rating, Pricing.
8. **Add for Review** → *Submit*.

## One thing left in the app itself

The `-qa-*` launch arguments documented in the root [README](../README.md) are
*not* wrapped in `#if DEBUG` — unlike the `-shot` scenes, which are — so they
exist in a Release build too. Nothing can reach them without a debugger attached,
so this is not a review risk, but wrapping them would be tidier and would take
the QA hooks out of the shipped binary. Left alone here because the README
documents them as working, and changing that is a separate decision.
